# Требования GITHUB-OPSEC: Microsoft Hyper-V

## Статус и границы
MVP реализует offline CLI и детерминированные правила для экспортированных evidence. Live Windows collector отложен; подключения и реальный аудит не выполнялись. Linux — только разработка, проверка документации и синтетических фикстур. Реальные проверки требуют отдельного Windows Server Hyper-V стенда с поддерживаемой виртуализацией. Продукт не выполняет remediation, эксплуатацию уязвимостей, изменение сетей, создание checkpoints, экспорт VM или восстановление.

## Функциональные требования
- R01: инвентаризация версии/редакции/сборки Windows Server, роли Hyper-V, обновлений и поддерживаемости конфигурации; неподдерживаемость явно отражается.
- R02: аудит host management plane: административные группы, делегирование, сервисные учетные записи, разделение обязанностей, отдельная сеть управления и доступ с доверенных рабочих станций.
- R03: WinRM: listeners, TLS, сертификаты, authentication, firewall scope, delegation и эффективные политики; отсутствие доказательства не означает безопасность.
- R04: VM/vSwitch/VLAN: поколения VM, типы switch, VLAN access/trunk, разрешенные сети, SR-IOV и иные обходные пути; настройки сверяются с утвержденной схемой изоляции.
- R05: Secure Boot, шаблон доверия, vTPM, encryption/key protector и Shielded VM/HGS оцениваются с учетом поколения VM, ОС гостя, версии хоста и модели поддержки. Наличие vTPM не доказывает shielding.
- R06: VHDX, AVHDX/checkpoints, конфигурации VM и backup: эффективные ACL, расположение, доступ по SMB, шифрование, отдельные права и защита резервных копий. Checkpoint не считается резервной копией.
- R07: журналирование: доступность и retention Hyper-V/WinRM/security событий, audit policy, централизованный сбор и контроль целостности; неизвестная доставка требует внешнего свидетельства.
- R08: readiness восстановления после ransomware: независимые/неизменяемые копии, разделение идентичностей, runbook, подтвержденный restore drill, RPO/RTO и проверка целостности. Конфигурация backup без протокола восстановления не дает pass.
- R09: воспроизводимый отчет с ID правила, временем UTC, scope, источником evidence, applicability, результатом и объяснением. Секреты и идентификаторы среды редактируются до экспорта.

## Контракт результата
Статусы MVP: pass, fail, unknown, not_run. Pass требует достаточного свежего evidence; fail — подтвержденного нарушения политики; unknown — недостаточных данных; сбой сбора дает unknown с причиной. Not_run означает отсутствие собранного раздела, исключение или неприменимость с объяснением, а не успех. Severity и confidence независимы. Политика и версия правил фиксируются в отчете. Выводы ограничены обследованным scope и временем сбора.

## Нефункциональные требования и приемка
Только явно разрешенный scope; минимальные права по источнику; read-only allowlist операций; таймауты и лимиты данных; отсутствие сохранения credentials. Запрещены автоматическое elevation, исправления и неявное включение remoting. Каждый источник должен иметь тест отказа доступа и unavailable case. Лаборатория подтверждает отсутствие изменений сравнениями до/после и журналами. Производительность и поддерживаемые версии утверждаются после лабораторных измерений; числовые SLA пока не заявляются.

## Приемка MVP
CLI audit/validate/rules, схема JSON 1.0, ограниченная загрузка, явные синтетические маркеры, 10 семейств правил HV-01..HV-10, JSON/Markdown, unit/integration tests, wheel/sdist и CI. Отсутствие evidence не дает pass. Политика MVP задается approved/expected/required полями evidence и freshness параметрами; это декларации владельца, не независимая аттестация.

## Не входит в MVP
Live collector, автоматическая проверка vendor support, network reachability/изоляции, effective AD ACL вычисления, подпись evidence, боевой аудит, исправления, полный guest hardening и гарантия восстановления. Первый выпуск prerelease до Windows лабораторной приемки.
