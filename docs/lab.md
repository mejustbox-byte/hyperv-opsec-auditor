# Лаборатория и проверка восстановления

## Два контура

Облачный Linux: Git, Python 3.12, документация, синтетический JSON и проверка контракта. Команды `.venv/bin/python -m unittest discover -s tests -v` и `.venv/bin/python tools/package_smoke.py` проверяют автономный обработчик и CLI, а не Hyper-V.

Windows: выделенный Windows Server с ролью Hyper-V и поддерживаемой аппаратной либо вложенной виртуализацией. Владелец проверяет CPU/SLAT, виртуализацию в прошивке, версию/редакцию хоста, гостей и вложенную платформу по документации Microsoft. Произвольная облачная VM не считается пригодной. Shielded VM/HGS требуют отдельной поддерживаемой инфраструктуры и доверия; отсутствие HGS не заменяется успешным результатом.

## Подготовка и сценарии

1. Зафиксировать владельца, письменную область, сборку/обновления, оборудование, поддерживаемый профиль и топологию. Только вымышленные учетные записи/данные; отключить маршруты в производственную среду.
2. Разделить сегменты управления, VM и резервного копирования; создать Gen1/Gen2 с подходящими гостями; утвердить Secure Boot/vTPM и профиль Shielded VM при поддержке.
3. Задать базовые права, WinRM, ACL, журналы и копирование. Нарушения создает владелец вне аудитора; продукт ничего не меняет.
4. Зафиксировать состояние до сбора; отдельно разрешенными средствами чтения предоставить проверенные данные; запустить автономный CLI; проверить матрицу, отказ доступа, таймауты и обезличивание, сравнить состояние после. События аудита от чтения учитывать отдельно.
5. Вручную восстановить исходное состояние; хранить протокол и очищенные данные вне публичного репозитория.

## Учебное восстановление без программ-вымогателей

Не запускать вредоносные программы. В изолированном контуре административным сценарием моделировать недоступность исходного хранилища и основных учетных данных. Восстановить VM из независимой копии по инструкции; проверить загрузку, приложения, контрольные суммы тестовых данных, изоляцию сети и отсутствие условий повторного заражения. Измерить RPO/RTO относительно утвержденных целей. Контрольные точки не заменяют резервные копии. Отдельно проверить восстановление ключей/доверия защищенных VM в поддерживаемом профиле.

Протокол: даты UTC, область/сборка, идентификатор копии без секретов, роли исполнителей, цели, шаги, свидетельства целостности, измерения, отклонения, проверяющий и срок действия. Разрушительные шаги требуют отдельного разрешения владельца стенда. Все реальные испытания Windows/восстановления пока не выполнены.

## Приемка MVP на Windows

1. Установить wheel в Python 3.12 venv, проверить `--version`, `validate`, `audit` на синтетических данных с фиксированным `--as-of`. Это только автономная проверка установки.
2. На поддерживаемом стенде подготовить реальные обезличенные данные HV-01..HV-10, отдельно утвердить ожидаемую политику и внешние проверки. Не копировать данные в Git.
3. Зафиксировать даты, сборку, профиль, права и исходное состояние. Выполнить `audit` с текущим UTC и сравнить выводы с независимой оценкой администратора.
4. Проверить Gen1/Gen2, поддерживаемые/неподдерживаемые профили, гостевые шаблоны Secure Boot, vTPM без Shielded VM, поддерживаемый HGS. Недоступность не заменять `pass`.
5. Независимо проверить сетевую изоляцию, эффективные права AD/хранилища, доставку журналов и неизменяемость копий. MVP только потребляет результаты.
6. Выполнить описанное восстановление; сравнить RPO/RTO/целостность с отчетом; зафиксировать актуальность, отказы и неполноту.
7. Сравнить состояние до/после. CLI не выполняет инфраструктурных операций; будущий сборщик отдельно проверяется на соблюдение перечня разрешенного чтения.

Синтетические тесты Linux и автономный CI Windows не равны этой процедуре. Все реальные пункты 2..7, поддерживаемая вложенная виртуализация и HGS/восстановление **НЕ ПРОВЕРЯЛИСЬ**.
